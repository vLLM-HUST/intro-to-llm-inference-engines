# 《大模型推理系统与实践》研究生课程教材

## 一、课程定位

本课程面向高年级研究生、博士生以及具备系统研究兴趣的工程型学生，围绕“大模型如何稳定、高效、可扩展地作为在线服务运行”这一核心问题，系统讲授现代大模型推理基础设施的基本概念、关键机制、主流系统设计方法与研究切入点。

与一般的模型导论课程不同，本课程并不把重点放在参数训练或模型效果调优上，而是把推理系统视为一个持续演化的状态化服务系统，重点讨论以下问题：

- 请求如何被组织、排队、调度并执行。
- KV Cache、检索结果、会话记忆等状态如何被保存、搬运和复用。
- 执行路径如何受到硬件拓扑、内存容量、通信代价和软件栈成熟度的共同制约。
- 一个局部优化为什么常常不能自动转化为端到端收益。
- 开源运行时、实验工作流与研究论文之间如何形成闭环。

## 二、适用对象与先修要求

建议选课学生具备以下基础：

- 操作系统、计算机体系结构、并行与分布式系统的基础知识。
- 深度学习基本概念，能够理解 Transformer、注意力机制和推理流程。
- 能够阅读系统论文，具备基本的 Python 或 C++ 工程阅读能力。

如果学生尚未系统接触大模型服务系统，可先补足以下三个前置概念：

1. Transformer 推理中的 prefill 与 decode 区别。
2. GPU 或其他加速器中的显存、带宽、kernel launch 与通信代价。
3. 在线服务中的吞吐、时延、尾时延、SLO 与多租户概念。

## 三、课程目标

完成本课程后，学生应能够：

1. 从系统视角描述一次大模型推理请求的完整生命周期。
2. 分析在线推理系统中的主要瓶颈来源，并区分计算瓶颈、内存瓶颈、通信瓶颈与调度瓶颈。
3. 理解 continuous batching、PagedAttention、prefill-decode 解耦、分层缓存、异构执行等核心机制。
4. 对经典论文进行问题建模、机制拆解、收益边界和实验可信性分析。
5. 基于 vLLM 或类似开源系统设计课程项目、复现实验或新的研究原型。

## 四、课程组织方式

课程采用“机制讲解 + 论文精读 + 系统案例 + 习题讨论 + 项目训练”的组织方式。推荐按 14 周学期制开展，每周 1 次课，每次课可按“概念讲授 60-75 分钟 + 论文/代码讨论 20-30 分钟 + 作业或实验布置 10-15 分钟”的节奏组织。

## 六、课程总图

可以把大模型推理基础设施理解为四层连续耦合的系统：

1. 工作负载层：请求到达模式、上下文长度、模型结构、工具调用、RAG 与智能体行为。
2. 控制层：准入、排队、路由、调度、资源配额与反馈控制。
3. 状态层：模型参数、KV Cache、知识缓存、会话记忆、统计信息与运行时元数据。
4. 执行层：算子、图执行、并行通信、设备放置、缓存层次与服务接口。

课程的基本判断是：

> 大模型推理系统的核心问题，并不是把某个算子单独做快，而是在动态负载、持续状态和异构硬件约束下，把整个服务链路组织为一个稳定可控的系统。

## 模块 1 导论：研究对象、系统边界与问题地图

### 1.1 为什么“大模型推理基础设施”是独立课程主题

随着大模型从离线演示走向持续在线服务，研究问题发生了明显迁移。早期讨论常集中在“模型能否生成合理结果”，而在真实部署中，系统侧问题逐步成为决定服务质量的主要因素：

- 用户更关心首 token 延迟是否稳定，而不是理论峰值吞吐是否足够高。
- 工程团队更关心多模型、多租户、多场景是否能在统一平台上共存。
- 研究者更关心一个新机制在真实工作负载和真实硬件条件下是否还能兑现收益。

因此，大模型推理基础设施不再只是“模型部署”的附属工程，而成为连接模型、系统与平台的独立研究对象。

### 1.2 本课程讨论的系统边界

本课程主要覆盖下列边界内的问题：

- 在线推理服务而非离线训练。
- 单请求执行与多请求并发的协同组织。
- 推理系统内部状态与外部知识状态的统一理解。
- 开源 serving runtime 与面向真实工作负载的评测方法。

本课程默认不深入讨论以下内容，但会在需要时建立接口：

- 模型训练、RLHF、预训练数据治理。
- 通用分布式训练框架内部实现。
- 纯算法侧的 prompt 工程或生成质量评价。

### 1.3 推理系统为何是“状态化系统”

推理系统不是无状态函数调用。它至少同时维护以下几类状态：

- 计算状态：当前 token 位置、batch 组成、执行阶段。
- 缓存状态：KV block、前缀缓存、激活缓存。
- 外部知识状态：检索结果、知识块、索引结构。
- 服务状态：队列长度、配额、优先级、SLO 统计、失败重试信息。
- 交互状态：多轮对话历史、工具调用上下文、会话记忆。

这些状态共同决定系统行为。很多性能问题不是出在单次 forward 本身，而是出在状态被长期保留、频繁搬运、错误放置或不能复用。

### 1.4 本模块讨论题

1. 为什么说大模型推理系统更接近“在线状态系统”而不是“批处理程序”？
2. 在真实部署中，哪些状态对象最容易成为瓶颈放大器？为什么？

## 模块 2 工作负载与评价指标：系统为何难以稳定优化

### 2.1 工作负载类型

大模型推理工作负载至少可以分为四类：

- 离线批推理：关注总吞吐与资源利用率。
- 在线对话服务：关注 TTFT、TPOT、P95/P99 与稳态吞吐。
- 检索增强服务：关注检索-注入-生成全链路时延。
- 智能体工作流：关注跨轮状态、工具调用与任务级完成时间。

不同工作负载带来的系统含义并不相同。例如，RAG 工作负载可能在检索侧放大时延波动，长上下文任务可能在 prefill 阶段放大显存与算力压力，而多智能体任务会同时放大队列波动和状态维护复杂度。

### 2.2 核心评价指标

常见指标包括：

- TTFT：用户看到第一个 token 的等待时间。
- TPOT：每个输出 token 的平均生成间隔。
- Throughput：单位时间完成的请求数或 token 数。
- Tail latency：P95、P99 等尾部时延。
- Goodput：满足服务目标的有效吞吐。
- Cost efficiency：单位吞吐所需成本。
- Stability：在波动负载下指标变化是否平稳。

### 2.3 为什么单点指标不够

一个优化即便提升了局部吞吐，也不意味着端到端更优。原因在于：

- 更大的 batch 可能提高平均吞吐，但会增加新请求等待时间。
- 更激进的缓存复用可能带来额外管理代价和尾时延抖动。
- 更快的局部 kernel 可能被通信等待或调度空转抵消。

课程中要反复建立的习惯是：

> 任何优化结论都要回答三个问题：优化了什么局部对象、影响了哪条全链路、最终由什么指标证明收益成立。

### 2.4 常见工作负载变化趋势

- 长上下文把容量问题从附属问题变成主问题。
- MoE 把负载均衡问题从 batch 内部扩展到设备拓扑级别。
- 多模态把请求形态从“统一 token 流”扩展到更复杂的异构输入。
- 智能体把单轮生成变成多阶段流水和跨轮状态写入问题。

### 2.5 本模块习题

1. 给定一个以 TTFT 为核心的在线服务，为什么极限吞吐并不是唯一优化目标？
2. 试比较对话服务与 RAG 服务在系统瓶颈上的主要差异。

## 模块 3 推理执行路径：从请求到 token 的全链路分解

### 3.1 一次请求的生命周期

一个典型请求会经历如下阶段：

1. API 接入与参数校验。
2. tokenizer 处理与输入规范化。
3. 请求进入队列并等待调度。
4. prefill 执行，生成首轮 KV 状态。
5. decode 迭代执行，不断追加新 token。
6. 流式返回结果，并在结束后回收资源。

### 3.2 prefill 与 decode 的本质差异

prefill 的特点：

- 计算密集。
- 直接决定首 token 延迟。
- 对长 prompt 特别敏感。

decode 的特点：

- 每轮计算较小，但需要频繁迭代。
- 更依赖 KV 状态长期驻留和低排队延迟。
- 更容易受到并发请求和调度噪声影响。

把二者混为同一种任务，是许多系统问题的根源之一。

### 3.3 批处理为何既带来收益也带来风险

批处理可以提高设备利用率，但也会带来三个风险：

- 排队等待被放大，短请求被长请求拖住。
- 共享状态对象增多，资源回收和隔离更复杂。
- 调度控制点减少，系统难以快速响应新请求。

### 3.4 continuous batching 的意义

continuous batching 的基本思想是：不等待整个 batch 全部完成后再重组，而是在每一轮或若干轮后重新决定下一轮 batch 组成。这一机制的价值在于：

- 新请求可以更快插入执行路径。
- 已完成请求可及时离开，释放资源。
- 调度器获得更高频率的控制机会。

### 3.5 本模块课堂实验建议

选择一个开源推理系统，记录以下数据并作图：

- 请求到达时间。
- 首 token 返回时间。
- 每轮 batch 大小变化。
- KV 占用变化趋势。

学生应通过实验回答：系统瓶颈究竟更像排队问题、容量问题还是执行路径问题。

## 模块 4 请求调度与服务编排

### 4.1 调度对象是什么

调度对象可以是：

- request 级对象。
- iteration 级对象。
- token 级对象。
- 更高层的会话、租户或服务副本。

不同调度粒度决定了系统的控制精细度和管理开销。

### 4.2 调度目标之间的冲突

调度通常需要同时面对以下目标：

- 最大化有效吞吐。
- 降低新请求等待。
- 控制尾时延。
- 保持公平性与资源隔离。
- 避免某类请求长期饥饿。

这些目标并不天然一致。一个只追求吞吐的调度器，通常很难在多租户服务里守住尾时延。

### 4.3 典型方法与代表论文

#### Orca

Orca 的代表性意义在于，它把调度时机推进到 iteration 级别，说明在线推理中的关键不是让单个请求尽快跑完，而是让队列持续可重组。

课堂讨论重点：

- Orca 改变的并不是模型计算本身，而是控制点的位置。
- 细粒度调度为何能缓解队头阻塞。
- selective batching 为什么需要配合状态保留机制。

#### vLLM

vLLM 在调度上的重要性不只来自 continuous batching，还来自它把调度和内存管理放在同一系统设计里考虑。课堂需要强调：

- 调度与内存不是分离问题。
- 如果 KV 管理方式不支持动态批处理，调度收益会被容量约束抵消。

### 4.4 调度作为控制环

一个更完整的调度视角应包括：

- 输入信号：到达率、长度分布、租户类型、设备利用率。
- 决策变量：准入、优先级、batch 上限、资源映射、路由目标。
- 反馈指标：TTFT、P99、违约率、吞吐、队列长度。
- 控制目标：在波动负载下维持稳态服务质量。

### 4.5 课堂讨论题

1. iteration-level 调度相比 request-level 调度的收益和代价分别是什么？
2. 在长短请求混合工作负载下，如何解释队头阻塞的系统放大效应？

## 模块 5 KV Cache 与状态管理

### 5.1 为什么 KV Cache 是推理系统核心对象

KV Cache 既不是简单的中间结果，也不是普通缓存。它具有以下特点：

- 它的增长与上下文长度和并发请求数直接相关。
- 它既服务于性能，也受容量约束严重影响。
- 它的组织方式会反过来塑造调度策略。

### 5.2 KV 的生命周期

KV 状态的生命周期通常包括：

1. prefill 生成。
2. decode 持续追加。
3. 可能的共享、复用或迁移。
4. 完成后释放或转入更低层存储。

系统设计时必须回答：

- KV 是否按连续地址组织。
- 是否允许分页或块式管理。
- 是否支持前缀共享或跨请求复用。
- 如何处理碎片、回收和淘汰。

### 5.3 PagedAttention 的系统意义

PagedAttention 的关键价值在于，把“逻辑连续的序列状态”映射到“物理离散的块式显存管理”上，从而缓解连续大块显存需求与内部碎片问题。课程中要引导学生理解：

- 这不是单一 attention kernel 的优化。
- 它本质上是一种状态组织方法。
- 该组织方法使 continuous batching 在更高并发下可持续工作。

### 5.4 前缀复用、知识缓存与会话记忆的统一视角

课程应鼓励学生把以下对象放在统一框架中理解：

- KV prefix sharing。
- RAG 中知识块缓存。
- 多轮会话中的长程记忆对象。

三者都具有“可复用状态对象”的属性。差别主要在于：

- 复用条件是否严格。
- 对一致性和正确性的要求是否不同。
- 访问频率与驻留时间是否相同。

### 5.5 DistServe 与 RAGCache

#### DistServe

DistServe 说明状态不仅要被保存，还可能需要跨阶段搬运。prefill 与 decode 解耦后，系统收益来自分阶段优化，但代价来自状态传输与协调。

#### RAGCache

RAGCache 说明外部知识并不是推理系统外部的“附加输入”，而是会变成系统内部需要管理和缓存的状态对象。

### 5.6 本模块习题

1. 为什么说 KV 管理方式会反向影响调度器能力边界？
2. 在什么意义上，知识缓存与 KV Cache 属于同类系统对象？

## 模块 6 推理系统架构：控制面、数据面与运行时边界

### 6.1 一个现代推理系统通常包含哪些部件

典型部件包括：

- API server。
- tokenizer 与请求规范化层。
- 调度器。
- 执行器与模型 runner。
- KV 管理器。
- 并行通信与分布式执行层。
- 监控、日志、回归与评测工具。

### 6.2 控制面与数据面的区分

控制面主要处理策略：

- 什么时候接收请求。
- 如何排队。
- 把请求发给谁。
- 何时扩容或限流。

数据面主要处理执行：

- 哪些 token 被计算。
- 哪些状态需要驻留、迁移或回收。
- 哪些 kernel、图执行或通信路径被触发。

研究时若不区分这两层，常会把策略问题和执行问题混在一起，导致问题定义不清。

### 6.3 为什么真实系统案例重要

只有进入真实开源系统，学生才能观察到：

- 论文中的机制如何映射到代码中的模块与接口。
- 一个优化为何需要和日志、指标、回归脚本同时出现。
- 代码中大量“非核心算法”部分为何决定了研究是否能复现。

### 6.4 课堂建议

本模块可安排一次代码导读，要求学生识别：

- 请求生命周期入口在哪里。
- 调度器如何拿到可观测信号。
- KV block 在哪里分配和回收。
- 指标输出如何与实验结论关联。

---

## 模块 7 执行优化与算子层协同

### 7.1 执行优化不等于 kernel 提速

执行优化通常包括：

- 算子融合。
- 图执行与编译。
- 内存布局调整。
- launch 开销控制。
- 形状管理与动态 batch 适配。
- 通信与计算重叠。

课程中要明确：这些工作只有在服务全链路中仍能保留收益，才算真正的系统优化。

### 7.2 FlexGen 的启发

FlexGen 说明“放不下模型”不是单纯的硬件不足问题，而是数据放置、访问顺序、压缩策略与批处理组织共同决定的系统问题。

课堂重点：

- 为什么简单 offload 往往不够。
- 为什么 I/O-aware 设计是正式系统问题。
- 为什么资源层次管理会改变最优执行路径。

### 7.3 PowerInfer 的启发

PowerInfer 说明异构执行并不只是“把一部分放到 CPU”，而是需要把预测、放置与执行组织成统一路径。课程里应引导学生思考：

- 什么时候激活稀疏性可以真正转化为系统收益。
- 什么时候跨设备传输会吃掉理论加速。
- 为什么硬件比例会决定方法边界。

### 7.4 本模块讨论题

1. 为什么“单点 kernel 更快”常常不能自动推出“服务更快”？
2. 在显存受限系统中，放置策略与批处理大小之间是什么关系？

---

## 模块 8 软硬协同与异构平台适配

### 8.1 为什么平台差异是系统差异

国产异构平台与主流 GPU 平台的差异，不只是驱动接口差异，而会体现在：

- 图执行语义不同。
- 算子库成熟度不同。
- 通信拓扑和互联带宽不同。
- host-device 数据路径代价不同。
- 调试、观测与回归工具成熟度不同。

因此，一个在某类平台上成立的优化，不应默认能平移到另一类平台。

### 8.2 适配的三个层次

课程建议把平台适配分成三个层次：

1. 能运行：补齐后端接口和基本功能。
2. 能优化：根据平台特性重组执行路径和状态管理方式。
3. 能验证：建立跨平台对比、公平实验与回归基线。

### 8.3 一个重要方法论

面对异构平台，研究者应该避免两个误区：

- 只把问题定义为“移植工程”。
- 只报告局部数值而不说明收益成立条件。

更合理的做法是显式回答：

- 平台差异改变了哪类瓶颈。
- 机制为何仍然成立或不再成立。
- 新平台上的收益窗口和失败条件是什么。

### 8.4 本模块习题

1. 为什么“在平台 A 上有效”并不足以说明某机制是通用系统贡献？
2. 请设计一个用于比较两类异构平台推理收益的最小实验框架。

## 模块 9 典型论文精读与比较方法

### 9.1 精读不是复述摘要

系统论文精读应至少回答：

- 论文究竟重新定义了什么问题。
- 论文引入的新控制点或新状态对象是什么。
- 收益来自哪个关键机制。
- 方法边界是什么。
- 实验是否足以支撑结论。

### 9.2 六篇代表论文的课程化组织方法

- Orca：调度粒度重构。
- vLLM：调度与内存协同组织。
- DistServe：prefill/decode 解耦与状态传递。
- RAGCache：知识对象缓存与检索-推理重叠。
- FlexGen：资源分层与 I/O-aware 执行路径。
- PowerInfer：激活预测驱动的异构协同执行。

课程不建议把它们讲成六个孤立故事，而应把它们嵌入三条主线：

- 请求组织与调度。
- 状态管理与复用。
- 执行路径与收益验证。

### 9.3 论文比较框架

建议学生从五个维度比较论文：

1. 主要瓶颈假设。
2. 核心机制与系统接口。
3. 引入的额外代价。
4. 实验工作负载与指标。
5. 可迁移性与可复现性。

## 模块 10 开源系统实践、课程项目与研究选题

### 10.1 为什么必须进入真实系统

只有进入真实系统，学生才会真正理解以下事实：

- 研究问题不是悬浮定义，而是由代码边界、系统接口和评测工作流共同塑造。
- 一个机制要进入真实运行时，往往需要配套日志、脚本、回归、文档和实验资产。
- 真正困难的问题，常常出现在“机制与系统结合处”，而不是单独的算法定义里。

### 10.2 课程项目建议方向

可选项目包括：

- 调度类：长短请求隔离、尾时延控制、动态配额。
- 状态类：KV 复用、分层缓存、记忆对象统一管理。
- 执行类：图执行优化、放置策略、异构协同路径。
- 评测类：工作负载生成、可观测性建设、回归验证。
- 平台类：后端适配、运行时接口、跨平台对比实验。

### 10.3 研究选题训练

课程鼓励学生用下面四步形成选题：

1. 先确定瓶颈对象。
2. 再确定可控变量。
3. 明确影响链路。
4. 设计可信实验。

一个合格选题应避免仅停留在“提出一个更快方法”的层面，而应能够说明：

- 为什么该问题在真实系统中重要。
- 为什么当前系统难以自动解决。
- 为什么提出的机制可实现、可验证、可扩展。

## 七、课程作业与项目体系

### 7.1 平时作业

建议布置 5 次平时作业：

1. 概念作业：课程导论与系统边界。
2. 生命周期作业：请求路径与瓶颈识别。
3. 论文精读作业：Orca/vLLM 或 DistServe/RAGCache。
4. 代码导读或复现实验作业。
5. 项目实验设计作业。

### 7.2 论文精读报告要求

精读报告不应写成“论文摘要复述”，而应至少包含：

- 论文研究问题及其成立前提。
- 核心机制与引入的新控制点。
- 可能的额外代价和系统边界。
- 实验是否足以支撑结论。
- 你认为最值得追问的一个开放问题。

### 7.3 课程项目要求

每位学生独立完成一个 MOD，围绕宿主支持的扩展点选择可复现的系统问题。推荐选题方向：

- 调度：尾时延控制、准入治理、批处理组织。
- KV：块管理、复用策略、分层驻留。
- 状态：知识缓存、会话记忆、对象统一抽象。
- 执行：异构放置、编译与图执行、数据路径优化。
- 工具：benchmark、可观测性、回归验证。

项目交付建议包括：

- 问题定义。
- 机制设计。
- 最小实现或可复现实验。
- 结果分析。
- 边界与失败案例说明。

### 7.4 MOD 项目评分

问题定义 20 分、实现质量 20 分、实验设计 25 分、结果解释 25 分、表达与复现 10 分。MOD 项目得分直接作为课程总评。[分项评分和提交节点](../site/tutorials/assessment/index.html)

## 八、课程总结

本课程的核心结论可以压缩为三点：

1. 大模型推理系统首先是状态化在线服务系统，而不是单次模型执行程序。
2. 请求调度、状态管理和执行路径优化并不是彼此独立的三类工作，而是共同决定服务质量的连续系统链路。
3. 真正有价值的研究，不只需要提出机制，更需要把机制放回真实运行时、真实工作负载和真实硬件边界中验证。

## 十、结课建议

对研究生而言，本课程最重要的收获不只是记住几个系统名称，而是形成一种系统研究习惯：

- 先识别状态对象。
- 再识别控制点。
- 进而分析全链路收益。
- 最后用可信实验支撑结论。

如果学生能够在阅读论文、进入代码和设计实验时持续保持这一视角，就已经真正进入了大模型推理基础设施研究的门槛。
