# Tutorial 4：KV Cache 与状态组织

## 本次联动位置

- 对应讲次：第 5 讲“KV Cache 管理”和第 6 讲“状态管理与记忆组织”。
- 对应实验：`experiments/nano-vLLM实验课/实验四_KV状态与缓存组织实验.md`。
- 参考代码：`code/nano-vllm-hust/nanovllm/engine/block_manager.py`、`code/nano-vllm-hust/nanovllm/engine/sequence.py`。
- 本 tutorial 负责状态视角的概念辨析，不替代实验课中的容量观测和日志记录。

## 目标

本 tutorial 的目标是把 KV 从“attention 的中间结果”提升为“推理系统中的长期状态对象”。学生完成后应能回答：

- KV 在哪里生成、驻留和释放。
- KV 组织方式会如何反向约束调度与并发。
- 为什么状态问题不能只靠 kernel 优化来解释。

## 本 tutorial 不做什么

- 不直接布置状态统计器实现。
- 不在这里要求填写容量观测表。
- 不把探针和真实收益混写在一起。

## 核心概念

- KV 是跨阶段持续存在的状态对象，而不是一次前向传播的临时量。
- 状态组织方式会反向约束并发和调度弹性。
- observe-only 探针只能说明潜在重叠，不能自动推出真实复用收益。

## 必答问题

1. 为什么 KV 会成为系统级问题，而不是单个 kernel 的局部问题。
2. 为什么状态压力经常先表现为排队与并发变化。
3. 为什么课程里要把 KV、会话记忆和知识缓存放到更统一的状态视角下讨论。

## 课堂追问

- 如果一个系统没有暴露完整分页结构，学生还能如何识别状态对象。
- 为什么“长上下文导致系统更卡”这句话本质上是状态判断，而不是长度判断。
- 如果探针发现前缀重叠，为什么仍然不能直接宣称有复用收益。

## 推荐阅读与观察

- `code/nano-vllm-hust/nanovllm/engine/block_manager.py`
- `code/nano-vllm-hust/nanovllm/engine/sequence.py`
- DistServe、RAGCache 等论文中关于状态对象的表述

观察重点：

- 哪些字段体现请求携带的状态。
- 哪些逻辑体现状态的生成、驻留与释放。
- 哪些地方暗示状态会影响后续调度和资源分配。

## 推荐产出

- 一条“状态 -> 并发/等待 -> 指标”的因果链。
- 一段 400-600 字辨析：什么是 observe-only 状态信号，什么是真实收益。

## 本 tutorial 应回答的问题

- 为什么状态视角能统一 KV、知识缓存和会话记忆。
- 为什么很多系统论文真正优化的是状态组织，而不是单个算子。
- 为什么课程里必须持续区分“观测到重叠”和“实现了复用”。
