# Tutorial 3：调度与连续批处理观察

## 本次联动位置

- 对应讲次：第 4 讲“请求调度机制”。
- 对应实验：`experiments/nano-vLLM实验课/实验三_调度与连续批处理实验.md`。
- 参考代码：`code/nano-vllm-hust/nanovllm/engine/scheduler.py`。
- 本 tutorial 负责调度 trade-off 的理论辨析，不展开具体实验步骤。

## 目标

本 tutorial 让学生从“系统正在算 token”进一步进入“系统正在如何决定算谁的 token”。重点是理解控制点，而不是罗列实验操作。

## 本 tutorial 不做什么

- 不直接给出 workload 构造命令。
- 不在这里布置参数修改或代码实现步骤。
- 不把结果表格写成 tutorial 正文的一部分。

## 核心概念

- 调度器控制的通常不是“算子快慢”，而是谁先获得执行机会。
- 连续批处理的收益来自调度粒度变化，而不是平白无故出现。
- 吞吐、公平性、短请求体验三者常常存在张力。

## 必答问题

1. 调度改变的究竟是顺序、并发方式，还是算子本身。
2. 为什么某些策略能提高吞吐，却不一定改善短请求体验。
3. 连续批处理真正改变的是哪一个系统对象。

## 课堂追问

- 如果一个系统没有显式写出 “continuous batching” 这个词，学生还能从什么现象判断它在做类似的事情。
- 为什么“长请求占位”是一个系统问题，而不只是 workload 偶然性。
- 在什么情况下，更高吞吐反而意味着更差的用户感知。

## 推荐阅读与观察

- `code/nano-vllm-hust/nanovllm/engine/scheduler.py`
- 第 4 讲相关课件与 Orca / vLLM 调度部分

观察重点：

- waiting、running、finished 如何分化。
- 何处体现新请求插入、老请求占位或状态回退。
- 哪些地方表明调度器在控制“谁先执行”。

## 推荐产出

- 一段 400-600 字说明：你认为调度器真正控制的对象是什么。

## 本 tutorial 应回答的问题

- 连续批处理为什么是系统控制点变化，而不是纯实现技巧。
- 为什么调度策略的解释必须同时看吞吐和等待。
- 为什么讲调度时必须回到请求生命周期和状态驻留。
