# Tutorial 1：最小运行与代码地图

## 本次联动位置

- 对应讲次：第 1-2 讲导论与指标建立，第 7 讲推理系统架构与代码边界。
- 对应实验：`experiments/nano-vLLM实验课/实验一_最小运行与代码地图.md`。
- 参考代码：`code/nano-vllm-hust/example.py`、`code/nano-vllm-hust/nanovllm/llm.py`、`code/nano-vllm-hust/nanovllm/engine/llm_engine.py`。
- 本 tutorial 只负责概念判断与代码职责辨析；运行、插桩和提交要求统一放到实验课文档中。

## 目标

本 tutorial 的目标只有两个：

1. 解释为什么最小运行链路是后续所有机制分析的前提。
2. 建立 nano-vLLM 的最小代码职责地图。

学生完成后应能回答：一次请求是从哪里进入系统、在哪里进入执行、又在哪里返回结果。

## 本 tutorial 不做什么

- 不提供逐步实验操作命令。
- 不要求提交日志和运行截图。
- 不要求修改代码实现。

这些内容统一交给对应实验课处理。

## 核心概念

- 请求入口不等于真正的控制点。
- 代码地图不是目录截图，而是职责判断。
- 如果不能说清“谁拥有请求状态”，后续调度和 KV 分析都会失焦。

## 必答问题

1. `example.py`、`LLM.generate`、`llm_engine.py` 三者分别处在哪一层职责上。
2. 第一个真正持有请求状态的对象更接近哪一类：API 封装、请求对象、调度循环，还是执行器。
3. 为什么课程一开始要强调“最短调用链”，而不是让大家泛读整个仓库。

## 课堂追问

- 如果一个同学只能说出文件名，但说不出职责，这算不算真的完成了代码地图。
- 为什么“请求进入系统”与“系统开始控制请求”不是同一个时刻。
- 如果把 `LLM` 当成最终控制点，会在后续分析里造成什么误判。

## 建议阅读与观察

- `code/nano-vllm-hust/example.py`
- `code/nano-vllm-hust/nanovllm/llm.py`
- `code/nano-vllm-hust/nanovllm/engine/llm_engine.py`

观察重点不是具体实现细节，而是：

- 哪一层只是包装接口。
- 哪一层开始组织请求对象。
- 哪一层开始真正推进执行。

## 推荐产出

- 一张代码职责表。
- 一段 300-500 字回答：当前看起来第一个控制点在哪里，为什么。

## 本 tutorial 应回答的问题

- 为什么课程一开始不先讲优化，而先讲入口、状态和职责。
- 什么叫“最小代码地图”。
- 为什么后续每次实验都要反复回到这张图上。

## 常见误区

- 只截图目录，不解释职责。
- 只说“看到了 engine/scheduler”，但说不出调用顺序。
- 一上来就追所有类和所有文件，结果失去主线。
