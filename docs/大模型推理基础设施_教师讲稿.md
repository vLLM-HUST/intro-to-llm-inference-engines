# 大模型推理基础设施：教师讲稿

## 一、使用原则

这份讲稿不再服务于一次 20-30 分钟报告，而是服务于完整课程授课。讲授时应遵循三条原则：

1. 每次课先建立问题，再引入机制，不要直接进入论文结论。
2. 每个模块至少讲清一个系统对象、一个控制点和一个收益边界。
3. 尽量把“为什么难”与“为什么这样设计”讲明白，再讲数值结果。

## 二、14 周授课节奏建议

建议按一个完整学期推进：

- 第 1-4 周：建立统一系统视角，完成课程导论、工作负载、指标、生命周期和调度基础。
- 第 5-8 周：进入 KV、状态管理、系统架构与执行路径优化。
- 第 9-11 周：进入异构平台、论文阅读方法与实验可信性训练。
- 第 12-14 周：进入代码实践、项目推进、课程总结与最终汇报。

建议在学期中明确三个检查点：

- 第 4 周前后：完成论文精读对象选择。
- 第 11 周前后：完成实验设计草案。
- 第 13-14 周：完成中期与最终项目汇报。

## 三、课程开场建议

第一讲开场不宜用“今天我来汇报”，而应改为课程化口径：

> 本课程要解决的问题是，如何把大模型从一个能生成文本的模型，组织成一个稳定、高效、可扩展、可验证的在线服务系统。

接着立刻明确课程对象：

- 不是纯模型算法课。
- 不是单纯工程部署教程。
- 而是一门围绕系统问题建模、机制理解和研究训练展开的课程。

## 四、逐模块授课提示

### 模块 1 导论

授课目标：

- 建立“推理系统是状态化系统”的总视角。
- 让学生理解课程为什么围绕调度、状态与执行路径展开。

建议讲法：

- 用一次真实推理请求作为引子。
- 不要从论文列表开始，而要从用户看到的服务现象开始。
- 强调首 token 等待、尾时延波动、缓存压力和系统稳定性之间的联系。

课堂提问：

- 用户为什么会感觉“这个模型很卡”？
- 这件事究竟更像模型问题还是系统问题？

### 模块 2 工作负载与指标

授课目标：

- 让学生意识到不同工作负载会重新定义系统瓶颈。
- 建立对 TTFT、TPOT、throughput、P99 和 goodput 的清晰区分。

建议讲法：

- 用表格比较对话、RAG、智能体、多租户服务四类场景。
- 强调“峰值吞吐高”与“服务质量稳定”不是同一个命题。

课堂提问：

- 为什么有些系统平均性能很好，但用户体验仍然差？

### 模块 3 执行路径

授课目标：

- 讲清 prefill 与 decode 的资源特征差异。
- 让学生形成请求生命周期的时序视角。

建议讲法：

- 现场画时序图。
- 标出队列点、计算点、状态生成点和资源释放点。

课堂提问：

- 如果把 prefill 和 decode 当成同一种任务调度，会出现什么问题？

### 模块 4 调度

授课目标：

- 让学生理解调度控制点的重要性。
- 区分 request-level 与 iteration-level 调度。

建议讲法：

- 先讲长短请求混部导致的队头阻塞。
- 再引出 Orca 与 continuous batching。
- 最后把调度上升为控制环而非队列算法。

课堂提问：

- 为什么调度粒度一变，系统能力边界就会跟着变？

### 模块 5 KV 与状态管理

授课目标：

- 把 KV 从“实现细节”提升为“系统对象”。
- 说明状态组织方式为什么会决定系统并发能力。

建议讲法：

- 先讲 KV 为什么大、为什么持续存在。
- 再讲分页、块管理、回收与复用。
- 然后把前缀复用、知识缓存、会话记忆放到统一框架下比较。

课堂提问：

- 为什么 KV 管理并不是只有内存工程意义？

### 模块 6 状态搬运与记忆组织

授课目标：

- 让学生理解状态不只需要保存，还需要搬运、共享和复用。

建议讲法：

- 用 DistServe 说明“解耦会引入状态传递成本”。
- 用 RAGCache 说明“外部知识会进入系统内部状态空间”。

课堂提问：

- 如果把知识检索看成完全外部模块，会忽略哪些系统问题？

### 模块 7 系统架构

授课目标：

- 让学生建立控制面和数据面的区分。
- 让学生能在代码里找到核心运行路径。

建议讲法：

- 选一个真实运行时作为案例。
- 不追求把所有代码细节讲完，而是强调模块边界和数据流。

### 模块 8 执行优化

授课目标：

- 纠正“优化等于 kernel 更快”的直觉。
- 讲清放置、I/O 与异构协同的重要性。

建议讲法：

- 用 FlexGen 和 PowerInfer 做对照。
- 每讲一个方法都要配一个“为什么不总是成立”的边界说明。

### 模块 9 异构平台适配

授课目标：

- 让学生理解平台差异如何改变系统设计。
- 让学生意识到验证方法同样属于研究贡献的一部分。

建议讲法：

- 先讲“能跑起来”与“能稳定优化”之间的差距。
- 再讲跨平台对比为何需要统一工作负载和指标。

### 模块 10 论文精读、项目与研究训练

授课目标：

- 把课程从知识传授过渡到研究训练。

建议讲法：

- 让学生尝试用“瓶颈对象-可控变量-影响链路-验证方法”的结构汇报项目。
- 鼓励学生把项目做成可复现实验或最小原型，而不是只写想法。

## 五、项目指导建议

教师在指导课程项目时，建议反复要求学生回答四个问题：

1. 你要优化的系统对象是什么。
2. 你真正改变的控制点是什么。
3. 你的收益会沿着哪条链路传递到端到端指标。
4. 什么结果会直接否定你的当前假设。

如果学生无法清楚回答这四点，通常说明选题还停留在想法层面，尚未进入可执行研究问题。

## 六、课堂组织建议

- 每次课尽量保留 10-15 分钟讨论时间。
- 每个模块至少留一个开放问题，不要只停在已有论文结论上。
- 课程中应反复提醒学生区分“观察到相关性”和“证明因果收益”。

## 七、常见误区提醒

1. 只从模型视角理解系统问题。
2. 只看平均值，不看尾时延和波动。
3. 只看一个局部机制，不看全链路代价。
4. 只看论文图表，不看问题假设和实验边界。
5. 只关心方法是否新颖，不关心是否能进入真实系统。

## 八、课程结束语建议

课程最后不应只总结“学了哪些论文”，而应回到方法论：

> 真正的大模型推理基础设施研究，不是把某个点做得更快，而是让整个系统在复杂负载、持续状态和异构约束下，稳定地跑得对、跑得快、跑得住。

这句话适合作为课程最后一讲的收束句，也适合作为后续课程邀请或对外介绍时的统一表述。
