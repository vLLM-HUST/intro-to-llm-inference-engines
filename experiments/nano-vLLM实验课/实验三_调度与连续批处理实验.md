# 实验三：调度与连续批处理实验

## 一、实验课定位

本节实验聚焦调度控制点。学生要从“系统正在执行 token”进一步进入“系统正在决定先执行谁”的层面。

本节实验强调观察 batch 形成、队列等待和策略 trade-off，而不是写一个复杂调度器。

## 二、本节实验目标

完成本节后，学生应能够：

- 说明当前调度器控制的对象是什么。
- 记录 batch 如何形成、扩展和回收。
- 比较不同 workload 与简单策略差异下的 TTFT、吞吐和等待时间。
- 说清调度改变的是“谁先被算”，而不一定是“算得更快”。

## 四、课前检查

- 学生已完成实验二，能区分 prefill 与 decode。
- 学生知道 waiting、running、finished 等基本状态概念。
- 教师可演示至少两类 workload 的运行结果。

## 五、建议课时安排

- 10 分钟：回顾生命周期里的调度位置。
- 20 分钟：教师示范 batch 观测日志。
- 25 分钟：学生记录两类 workload 的调度行为。
- 20 分钟：尝试一项最小策略改动或参数改动。
- 10 分钟：讨论 trade-off。
- 5 分钟：说明提交要求。

## 六、本节核心问题

调度改变的到底是“算得更快”，还是“谁先被算、谁先完成、谁先感知到结果”？

## 七、实验步骤

### 步骤 1：确定观测对象

要求学生在调度循环中记录：

- waiting 队列长度
- running 集合大小
- 当前 batch 中的 request_id
- 每个请求的 prompt_len
- 每个请求已经生成的 token 数

### 步骤 2：设计 workload

至少准备两类 workload：

1. 同质 workload：请求长度接近。
2. 异质 workload：长短请求混合。

如条件允许，可增加：

3. 突发 workload：短时间内集中到达。

### 步骤 3：设计对照策略

可选方式：

- 修改最大 batch size。
- 修改每轮允许接纳的新请求数。
- 修改 decode 过程中是否插入新请求。
- 实现一个最小的短请求优先插入规则。

要求任何改动都必须写清：

- 改的是哪个控制点。
- 预期影响哪类指标。
- 哪个结果会推翻这个预期。

### 步骤 4：记录结果

建议表格：

| workload | policy | batch_limit | TTFT | throughput | queue_wait | short_finish | long_finish | 解释 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| homogeneous |  |  |  |  |  |  |  |  |
| heterogeneous |  |  |  |  |  |  |  |  |
| bursty |  |  |  |  |  |  |  |  |

### 步骤 5：整理 batch 观测日志

至少保留一段能看清下列现象的日志：

- 新请求何时进入 batch。
- 长请求是否持续占位。
- 短请求是否因为插入策略受益或受损。

## 八、课堂讨论问题

1. 在你的观测里，调度器主要控制的是顺序、公平性还是资源利用率。
2. 为什么有些策略吞吐更高，但短请求体验更差。
3. 连续批处理的收益来自哪里，代价又体现在哪些指标上。

## 九、常见错误

- 只比吞吐，不比等待时间和短请求完成时间。
- 改了参数却没有说明控制点。
- 没有记录 batch 形成过程，却直接解释调度效果。
- 把策略收益写成绝对结论，没有给出失败条件。

## 十、课后提交要求

1. 一份 batch 观测日志。
2. 一张至少两类 workload 的结果对比表。
3. 一页分析，解释 trade-off 与用户体验关系。
4. 如做了策略改动，附最小 diff 或关键代码说明。

## 十一、评分重点

- 是否真的观察到了调度行为，而不是只看最终数字。
- 指标选择是否覆盖等待、公平性和吞吐至少两个维度。
- 解释是否回到控制点，而不是停在“更快/更慢”。
